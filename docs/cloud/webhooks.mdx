<Note>
    Incoming webhooks are in preview.
</Note>

An incoming webhook is a URL that lets an external system, such as GitHub, Linear, or Slack, invoke one handler of a service in your Restate Cloud environment.
Every `POST` request to the URL starts an invocation of that handler, with the request body as its input.

<Warning>
    Anyone who has the URL can invoke the handler.
    The URL does not prove who sent a request, so verify the sender in your handler, usually by checking the signature the sender adds to each request.
</Warning>

## Create a webhook

<Steps>
<Step title="Register the target service">
A webhook invokes one handler of a public [service](/foundations/services#basic-service).
[Register the deployment](/services/versioning) that contains the handler before you create the webhook.

Virtual objects and workflows can't be webhook targets. To process events per key, [forward them to a virtual object](#handle-retries-and-slow-work).
</Step>
<Step title="Create the webhook">
In the Restate Cloud UI, open your environment's **Integration & API keys** page and create an incoming webhook.
Choose the service, the handler, and the [delivery mode](#choose-a-delivery-mode).
</Step>
<Step title="Give the URL to the sender">
Copy the webhook URL and paste it into the sender's webhook settings.
Admins can copy the URL again later.
</Step>
</Steps>

A webhook is bound to the names of its service and handler.
If you remove or rename the service or handler, deliveries fail with `503`, and Restate Cloud gives no warning.
To point the sender at a renamed handler, create a new webhook and give its URL to the sender.

Deleting a webhook stops its deliveries.
Requests usually stop reaching your handler within 30 seconds. If the Restate Cloud control plane is unavailable, this can take up to an hour.

## Choose a delivery mode

You choose the delivery mode when you create the webhook, and you can't change it later.
To switch modes, create a new webhook and give its URL to the sender.

| | Async | Sync |
|---|---|---|
| **The sender receives** | `202 Accepted` as soon as Restate has accepted the invocation, never the handler's result | The handler's response, as for a regular [HTTP call](/services/invocation/http): `200` with the return value, or the handler's error status |
| **Time limit** | None | The handler must respond within 30 seconds |
| **Use it for** | Senders that only need an acknowledgement, and long-running handlers | Senders that need a reply or exactly HTTP `200`, such as Linear, Slack URL verification, and Slack slash commands |

## How requests reach your handler

- Webhooks accept only `POST` requests.
- The body can be up to 1 MiB and needs a `Content-Length` header. Restate Cloud refuses chunked bodies without one.
- The URL path must be exactly as issued.
- Restate Cloud forwards the query string, except the `delay` and `limit-key` parameters. Your handler can read the query string at the end of the `x-restate-ingress-path` header.
- Your handler receives the body byte for byte.
- Your handler reads the sender's headers from `ctx.request().headers`, with lower-case names.
- Restate Cloud drops `Authorization`, `Cookie`, hop-by-hop headers such as `Connection` and `Transfer-Encoding`, and headers that start with `x-restate-` or `x-restatecloud-`.
- Restate stores the forwarded headers with the invocation, signature headers included.
- Restate Cloud adds the `x-restatecloud-webhook-id` header, which holds the ID of the webhook that received the request.
- Each webhook is rate limited to 100 requests per second, with bursts of up to 200.

The sender receives one of these responses:

| Status | Meaning |
|---|---|
| `202` | Async mode: Restate accepted the invocation. The body is `{"invocationId": "...", "status": "Accepted"}`. |
| `200` or the handler's error status | Sync mode: the handler's response. |
| `404` | The URL is wrong, or the webhook was deleted. |
| `405` | The request is not a `POST`. |
| `411` | The request has no `Content-Length` header. |
| `413` | The body is larger than 1 MiB. |
| `429` | The webhook's rate limit is exceeded. Retry after the number of seconds in `Retry-After`. |
| `502` | Your environment is unreachable or failed to accept the request. |
| `503` | The target service or handler is not registered, or Restate Cloud can't look up the webhook right now. |

## Write the handler

The examples on this page use the TypeScript SDK.
A webhook handler differs from a regular handler in three ways:

- **It accepts any content type and receives the raw body.** Declare the input as `restate.serde.binary` and set `accept: "*/*"`. Senders post JSON, form-encoded data, or other formats, and a handler that only accepts JSON rejects everything else. The raw bytes are also exactly what the sender signed.
- **It verifies the sender.** Compute the signature over the raw body and compare it with the one in the request headers, in constant time. If they don't match, throw a [terminal error](/develop/ts/error-handling#terminal-errors) with `errorCode: 401`. Restate doesn't retry the invocation, and in sync mode the sender receives the `401`.
- **It hands off the work and returns.** See [Handle retries and slow work](#handle-retries-and-slow-work).

This handler receives GitHub pull request events:

```typescript TypeScript {"CODE_LOAD::ts/src/cloud/webhooks.ts#github"} 
// Compares a computed signature with the one the sender sent, in constant time
function signatureMatches(expected: string, received: string | undefined) {
  if (received === undefined) return false;
  const a = Buffer.from(expected);
  const b = Buffer.from(received);
  return a.length === b.length && timingSafeEqual(a, b);
}

const gitHubWebhook = restate.service({
  name: "GitHubWebhook",
  handlers: {
    receive: restate.handlers.handler(
      // Accept any content type and receive the body as raw bytes
      { input: restate.serde.binary, accept: "*/*" },
      async (ctx: restate.Context, body: Uint8Array) => {
        const headers = ctx.request().headers;

        // Verify the signature over the raw body
        const secret = process.env.GITHUB_WEBHOOK_SECRET!;
        const expected =
          "sha256=" + createHmac("sha256", secret).update(body).digest("hex");
        if (!signatureMatches(expected, headers.get("x-hub-signature-256"))) {
          throw new restate.TerminalError("Invalid signature", {
            errorCode: 401,
          });
        }

        // Forward the work, once per delivery, and return right away
        if (headers.get("x-github-event") === "pull_request") {
          const event: PullRequestEvent = JSON.parse(
            new TextDecoder().decode(body)
          );
          const key = `${event.repository.full_name}#${event.number}`;
          ctx.objectSendClient(pullRequest, key).onEvent(
            event,
            restate.rpc.sendOpts({
              idempotencyKey: headers.get("x-github-delivery"),
            })
          );
        }
      }
    ),
  },
});
```

## Handle retries and slow work

Senders retry deliveries that fail or time out, and each retry starts a new invocation of your handler.
Senders also stop waiting after a few seconds, so in sync mode a slow handler makes the sender retry.

To process each delivery once:

1. Verify the request.
2. [Send](/develop/ts/service-communication#sending-messages) the actual work to another handler, with an [idempotency key](/develop/ts/service-communication#using-an-idempotency-key) built from the sender's delivery ID. Restate starts the work once per key, so a retried delivery doesn't run it again.
3. Return right away.

To process the events of one issue, pull request, or channel one at a time and in order, send them to a [virtual object](/foundations/services#virtual-object) keyed by that ID, as the examples on this page do.

| Sender | Delivery ID | Response time limit | Retries |
|---|---|---|---|
| GitHub | `x-github-delivery` header | 10 seconds | None automatically. A manual redelivery keeps the delivery ID. |
| Linear | `linear-delivery` header | 5 seconds | Up to 3 times, after 1 minute, 1 hour, and 6 hours |
| Slack | `event_id` in the body | 3 seconds | Up to 3 times |

If a sender sets an `Idempotency-Key` header, Restate deduplicates requests to the same webhook that carry the same key, so a retry doesn't start a second invocation.
In async mode, the sender then receives `"status": "PreviouslyAccepted"`.

## Senders

### GitHub

1. In your repository or organization settings, add a webhook with the webhook URL as the **Payload URL**.
2. Set **Content type** to `application/json`.
3. Set a **Secret**, and give your service the same value, `GITHUB_WEBHOOK_SECRET` in the [example above](#write-the-handler).

Both delivery modes work, because GitHub accepts any `2xx` response.
GitHub signs each delivery in the `x-hub-signature-256` header: `sha256=` followed by the hex HMAC-SHA256 of the body.

GitHub doesn't retry failed deliveries automatically. You can redeliver them from the webhook's settings in GitHub, and the redelivery keeps its `x-github-delivery` ID.

### Linear

Use **sync** mode. Linear treats any response other than HTTP `200` as a failure, including the `202` of async mode.

In Linear, create a webhook in your workspace's API settings with the webhook URL, and give your service its signing secret.
Linear signs each delivery in the `linear-signature` header, the hex HMAC-SHA256 of the body.
The `webhookTimestamp` field in the body is the time Linear sent the delivery, in milliseconds.

```typescript TypeScript {"CODE_LOAD::ts/src/cloud/webhooks.ts#linear"} 
const MAX_AGE_MS = 60_000;

const linearWebhook = restate.service({
  name: "LinearWebhook",
  handlers: {
    receive: restate.handlers.handler(
      { input: restate.serde.binary, accept: "*/*" },
      async (ctx: restate.Context, body: Uint8Array) => {
        const headers = ctx.request().headers;

        const secret = process.env.LINEAR_WEBHOOK_SECRET!;
        const expected = createHmac("sha256", secret)
          .update(body)
          .digest("hex");
        if (!signatureMatches(expected, headers.get("linear-signature"))) {
          throw new restate.TerminalError("Invalid signature", {
            errorCode: 401,
          });
        }

        const event: LinearEvent = JSON.parse(new TextDecoder().decode(body));
        const now = await ctx.date.now();
        if (Math.abs(now - event.webhookTimestamp) > MAX_AGE_MS) {
          throw new restate.TerminalError("Delivery too old", {
            errorCode: 401,
          });
        }

        if (event.type === "Issue") {
          ctx.objectSendClient(linearIssue, event.data.id).onEvent(
            event,
            restate.rpc.sendOpts({
              idempotencyKey: headers.get("linear-delivery"),
            })
          );
        }
      }
    ),
  },
});
```

Linear recommends rejecting deliveries whose `webhookTimestamp` is more than a minute old.
Your handler can start later than the delivery arrived, for example if your deployment was unavailable, so widen `MAX_AGE_MS` if this rejects deliveries you want to keep.
`ctx.date.now()` records the time on the first attempt, so a retry of the same invocation compares against the same time.

### Slack

Use **sync** mode. Slack verifies an Events API request URL by sending a challenge that your handler must return, and it shows the response to a slash command as the reply.

Each Slack request URL needs its own webhook: create one for the `events` handler below and use it as the Events API request URL, and one for the `command` handler and use it as the slash command's request URL.

Slack signs each request in the `x-slack-signature` header: `v0=` followed by the hex HMAC-SHA256 of `v0:<timestamp>:<body>`, keyed with your app's signing secret.
`<timestamp>` is the value of the `x-slack-request-timestamp` header. Slack recommends rejecting requests that are more than five minutes old.

```typescript TypeScript {"CODE_LOAD::ts/src/cloud/webhooks.ts#slack"} 
const SLACK_MAX_AGE_SECONDS = 5 * 60;

async function verifySlackRequest(ctx: restate.Context, body: Uint8Array) {
  const headers = ctx.request().headers;
  const timestamp = headers.get("x-slack-request-timestamp") ?? "";

  const secret = process.env.SLACK_SIGNING_SECRET!;
  const expected =
    "v0=" +
    createHmac("sha256", secret)
      .update(`v0:${timestamp}:`)
      .update(body)
      .digest("hex");
  const ageSeconds = (await ctx.date.now()) / 1000 - Number(timestamp);
  if (
    !signatureMatches(expected, headers.get("x-slack-signature")) ||
    Math.abs(ageSeconds) > SLACK_MAX_AGE_SECONDS
  ) {
    throw new restate.TerminalError("Invalid signature", { errorCode: 401 });
  }
}

const slackWebhook = restate.service({
  name: "SlackWebhook",
  handlers: {
    // Request URL of the Events API subscription
    events: restate.handlers.handler(
      { input: restate.serde.binary, accept: "*/*" },
      async (ctx: restate.Context, body: Uint8Array) => {
        await verifySlackRequest(ctx, body);
        const payload = JSON.parse(new TextDecoder().decode(body));

        if (payload.type === "url_verification") {
          return { challenge: payload.challenge };
        }
        if (
          payload.type === "event_callback" &&
          payload.event.type === "message"
        ) {
          ctx
            .objectSendClient(slackChannel, payload.event.channel)
            .onEvent(
              payload.event,
              restate.rpc.sendOpts({ idempotencyKey: payload.event_id })
            );
        }
        return {};
      }
    ),

    // Request URL of a slash command
    command: restate.handlers.handler(
      { input: restate.serde.binary, accept: "*/*" },
      async (ctx: restate.Context, body: Uint8Array) => {
        await verifySlackRequest(ctx, body);
        const form = new URLSearchParams(new TextDecoder().decode(body));

        return {
          response_type: "ephemeral",
          text: `Received ${form.get("command")} ${form.get("text")}`,
        };
      }
    ),
  },
});
```

- `events` answers the `url_verification` request by returning `{ challenge }`, and forwards message events with their `event_id` as the idempotency key. Slack expects a response within 3 seconds.
- `command` receives the form-encoded slash command and returns the reply, which Slack expects within 3 seconds. For longer work, send it to another handler and post the result to the command's `response_url` later.

## Limitations

- Senders that verify the URL with a `GET` or `PUT` request don't work, because webhooks accept only `POST`.
- Bodies larger than 1 MiB are refused, even if the sender allows larger ones. GitHub, for example, sends payloads of up to 25 MB.
- Senders that sign the full URL, such as Twilio and Square, need extra work: your handler never sees the webhook URL, so read it from your own configuration to verify the signature.
- Virtual objects and workflows can't be targets. Point the webhook at a service handler that forwards to the object.
